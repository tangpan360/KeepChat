# Architecture Principles

## 总体原则
- 先按长期分层设计，再按当前版本轻量实现。
- 前期采用模块化单体，不提前微服务化。
- 能复用成熟基础设施就复用，但产品核心对象与业务规则必须自己掌控。
- AI 框架可以深度使用，但不应直接成为整个产品的数据骨架。

## 系统分层
### 1. 客户端层
包含：
- Chrome 侧边栏插件
- 未来的论文阅读/编辑 Web 平台

职责：
- 聊天 UI
- 引用卡片
- 图片上传/拖拽
- 网页内容采集
- 历史会话展示
- 自动聚焦等交互体验

### 2. 应用接入层
职责：
- 统一 API 入口
- 鉴权校验
- 参数校验
- 请求路由
- 流式输出协议

要求：
- 前端只依赖产品 API，不依赖内部技术实现。

### 3. 领域业务层
核心对象建议围绕：
- `User`
- `Conversation`
- `Message`
- `Attachment`
- `ContextItem`
- `Document`
- 后续的 `EditTask`、`DiffSuggestion`

职责：
- 定义产品业务规则
- 定义消息、附件、引用、文档之间的关系
- 保持产品主模型稳定

### 4. AI 能力层
当前建议以 LangChain 为主要实现框架。

职责：
- 模型调用
- 对话组织
- memory / persistence
- streaming
- RAG
- tool / agent
- 工作流编排

原则：
- 可以以 LangChain 为核心 AI 实现。
- 但产品历史、用户体系、会话归档、附件和文档归属不应完全交给 LangChain 内部结构管理。
- LangChain 更适合作为 AI 引擎层，而不是整个插件产品的数据和交互骨架。
- LangChain / LangGraph 的 persistence、memory、checkpointer 更适合服务 AI 运行时状态，不应直接替代产品主存储。
- 产品正式数据仍应以自己的会话、消息、附件、上下文和配置模型为准，再按需映射到 LangChain 的运行时输入。

### 5. 基础设施层
职责：
- Auth
- Database
- Storage
- Queue
- Vector DB
- Logging / Monitoring

当前倾向：
- 尽量复用成熟平台，例如 Supabase 一类，用于鉴权、数据库和存储。

## 当前推荐实现思路
- 客户端：Chrome 插件先行，未来再接独立 Web 平台。
- 业务后端：一个主应用，内部按模块分层。
- AI 能力：LangChain 作为主要 AI 编排实现。
- 基础设施：优先使用成熟平台承接 auth、db、storage。
- 重任务：后期通过 worker 处理 PDF 解析、网页抓取、embedding、索引等任务。

## 模块边界原则
- 前端不直接依赖 LangChain 数据结构。
- 业务层不直接写死具体存储平台。
- 网页处理、PDF 处理、检索增强、编辑器改写应保持模块化，不要揉成一个大模块。
- 流式输出应定义产品自己的事件格式，而不是直接透传某个模型或框架的原始返回。

## 解耦目标
未来允许替换但不影响整体产品设计的内容包括：
- 模型供应商
- 向量库
- AI 编排实现
- 后端框架
- 基础设施服务商

前提是：
- 产品 API 稳定
- 领域模型稳定
- 具体框架只存在于实现层，而不是产品主结构里

## 微服务判断
- 前期不追求微服务。
- 前期追求的是模块边界清晰的单体架构。
- 只有在 PDF 解析、AI 编排、检索索引等模块变重后，再按需拆分服务。
