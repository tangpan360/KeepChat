# V1 Implementation Plan

## 目的
本文件用于把 KeepChat 当前阶段的设计文档收敛为一份可执行的实现计划，帮助后续真正进入产品开发，而不是继续停留在抽象设计层。

本文件关注：
- 第一批先做什么
- 开发顺序怎么安排
- 哪些能力先做最小版
- 哪些能力暂时不做
- 什么时候可以认为 V1 的最小链路已经跑通

本文件不展开数据库表、最终 API 路径和 UI 视觉细节。

## 当前阶段目标
先做出一个可以真实跑通的最小产品链路：
- 能打开侧边栏
- 能发文本消息
- 能得到流式回复
- 能创建和切换会话
- 能切换模型
- 能支持最基本的图片问答
- 能通过 `options` 页面配置基本动作与 BYOK

在此基础上，再逐步补网页增强能力。

## 当前实现原则
- 先跑通主链路，再补增强能力
- 优先实现“真正能用”的最小版本，不追求第一批就很完整
- 能简单就先简单，不提前做复杂抽象
- 当前优先做 V1 核心能力，不把后续优先能力一起压进第一批开发

---

## 一、推荐开发顺序总览

建议按下面顺序推进：

### 阶段 1：插件基础壳子
- 搭建 Chrome 原生 `sidePanel`
- 建立最基础的页面结构
- 建立最基础的状态管理骨架

### 阶段 2：最小文本问答链路
- 输入文本
- 发送消息
- 后端接收
- AI 调用
- 流式展示回复

### 阶段 3：历史会话与模型切换
- 新建对话
- 会话列表
- 切换会话
- 当前默认模型切换

### 阶段 4：图片问答最小版
- 图片上传 / 拖拽
- 图片能力校验
- 图文联合提问

### 阶段 5：Options 页最小版
- BYOK 入口
- 自定义动作最小配置能力

### 阶段 6：网页增强第一批
- 选中文本悬浮按钮
- `引用`
- `解释`
- 自定义动作自动发送
- 引用托盘

---

## 二、阶段 1：插件基础壳子

### 目标
先把插件最基本的运行外壳搭起来，让后续所有功能都有承载位置。

### 当前建议先做
- Chrome 插件基础清单
- side panel 页面
- 最基础布局
- 聊天主区占位
- 历史会话区占位
- 输入区占位

### 这一阶段不追求
- 完整视觉风格
- 完整设置体系
- 网页增强能力

### 完成标志
- 插件能在本地正常加载
- side panel 能正常打开
- 基础页面结构可见

---

## 三、阶段 2：最小文本问答链路

### 目标
先跑通最关键的主链路：文本提问 -> 后端 -> 模型 -> 流式回复。

### 当前建议先做
- 输入框文本输入
- 发送按钮
- 前端请求后端
- 后端接入 LangChain 对话调用
- 流式回复展示
- 请求中状态
- 请求失败状态

### 这一阶段暂时可以简化
- 不用先做复杂消息操作
- 不用先做网页增强
- 不用先做高级配置页

### 完成标志
- 用户能在侧边栏输入问题
- 模型能返回流式答案
- 能在界面里连续问答

---

## 四、阶段 3：历史会话与模型切换

### 目标
让聊天从“单轮原型”升级成“可持续使用的对话工具”。

### 当前建议先做
- 新建对话
- 会话列表加载
- 切换会话
- 当前默认模型切换
- 每条模型消息显示真实模型名

### 列表先做的字段
- 标题
- 当前默认模型
- 最近更新时间
- 消息总数

### 暂时可以后放的内容
- 会话重命名
- 会话删除
- 会话编辑高级能力

### 完成标志
- 用户可以创建多个会话
- 会话切换后能加载对应历史
- 模型切换可以影响下一次发送

---

## 五、阶段 4：图片问答最小版

### 目标
让产品具备基础多模态能力。

### 当前建议先做
- 图片上传
- 图片拖拽到侧边栏
- 待发送图片展示
- 图片与文本一起发送
- 当前模型图片能力校验

### 能力校验规则
- 当前提交带图片时，必须用支持图片的模型
- 默认只携带最近 `10` 轮历史上下文，以控制 token 成本
- 如果当前模型不支持“当前提交内容 + 最近 10 轮历史上下文”，则直接提示切换模型
- 当前阶段不做自动兼容、自动裁剪或自动降级处理

### 暂时可以不做
- 图片来源复杂分类
- 图片批量管理
- 高级附件面板

### 完成标志
- 用户能上传图片并得到图文问答结果
- 不支持图片的模型会被正确拦截和提示

---

## 六、阶段 5：Options 页最小版

### 目标
给用户一个基础配置入口，支持当前产品最重要的可配置能力。

### 当前建议先做
- 打开 `options` 页面
- BYOK 输入入口
- 自定义动作列表
- 动作名称与提示词配置
- 动作启用状态
- 动作排序

### 暂时可以不做
- 动作分组
- 模板导入导出
- 大量高级设置

### 完成标志
- 用户可以配置自己的 API key
- 用户可以新增并保存自定义动作

---

## 七、阶段 6：网页增强第一批

### 目标
在最小聊天能力稳定之后，再补产品差异化最强的网页增强能力。

### 当前建议先做
- 网页选区悬浮按钮
- 默认按钮：`引用`、`解释`
- 自定义动作入口
- 引用托盘
- 多段引用
- 删除单段引用
- 输入框补充问题后统一发送

### 当前建议暂时不做
- 站点级开关
- 当前网页整体问答细节
- 网页答案定位与高亮

### 完成标志
- 用户能在普通网页中选中文字
- 悬浮按钮能出现
- `引用` 能进入托盘
- `解释` 和自定义动作能自动发送

---

## 八、当前明确延后的能力
以下能力当前不进入第一批实现：
- 当前网页整体问答的完整逻辑
- 网页上下文开关完整状态设计
- 网页答案定位与高亮
- 多网页问答
- PDF 导入与问答
- 多文档 RAG
- 复杂 agent 工作流
- 论文平台能力

---

## 九、当前最小可运行版本定义

如果以下能力都已可用，就可以认为 V1 的最小版本已经跑通：

- side panel 可打开
- 文本聊天可正常使用
- 流式回复可展示
- 可新建与切换会话
- 可切换模型
- 图片问答可用
- `options` 页面可配置 BYOK 与基础动作

注意：
- 这不等于完整 V1 全量交付
- 这表示产品已经具备“开始真实使用与继续迭代”的基础

---

## 十、当前建议的开发节奏

### 推荐节奏
1. 先做插件基础壳子
2. 跑通最小文本问答
3. 补会话列表和模型切换
4. 补图片问答
5. 补 `options` 页面最小版
6. 再进入网页增强第一批

### 不推荐的节奏
- 一开始同时做聊天、图片、网页增强、PDF、RAG
- 一开始就追求完整视觉设计
- 一开始就设计复杂微服务拆分

---

## 十一、当前阶段的完成标准
当前阶段的目标不是“一次做完 KeepChat”，而是：

- 把最小聊天产品做出来
- 把关键数据流跑通
- 把模型切换与图片校验做顺
- 给网页增强能力预留好位置

如果这几点能跑通，后续继续加网页增强、网页问答和更重的知识能力就会顺很多。

## 当前使用建议
- 如果后续开始真正拆开发任务，应先按本文件的阶段顺序推进。
- 如果某个阶段内部再次拆任务，优先保证主链路先跑通。
- 如果中途发现功能范围变化较大，应先回看 `v1-scope.md` 和 `feature-structure.md`，再决定是否调整实现计划。
