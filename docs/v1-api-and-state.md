# V1 API and State

## 目的
本文件用于定义 KeepChat 在当前阶段的接口边界与状态流转方式，帮助后续进入具体开发时保持前端、后端和 AI 编排层的一致理解。

本文件关注：
- 插件端需要发起哪些核心请求
- 后端需要返回哪些核心结果
- 流式回复如何组织
- 本地状态与云端状态分别在何时更新
- 图片、引用托盘、模型切换等能力如何进入同一条请求链路

本文件不展开具体框架代码、数据库表字段或最终 API 路径命名。

## 当前阶段原则
- 前端只依赖产品 API，不直接依赖 LangChain 内部结构
- 产品主数据以自己的会话、消息、附件、上下文模型为准
- LangChain 主要承担 AI 调用、对话编排与运行时状态能力
- 本地状态用于提升交互体验，云端状态用于保存正式数据
- V1 先保证核心链路清晰，不提前设计复杂接口体系

## 顶层交互链路
当前产品的主链路可以概括为：

1. 插件端采集用户输入
2. 插件端组装当前待发送状态
3. 插件端调用后端接口
4. 后端校验请求并组织 AI 输入
5. AI 层调用当前模型
6. 后端流式返回结果
7. 插件端更新消息展示与本地状态
8. 后端写入正式会话历史

---

## 一、插件端核心状态

### 1. 当前会话状态
用于表示当前正在查看和继续对话的会话。

应包含：
- 当前会话标识
- 当前会话标题
- 当前默认模型
- 默认历史窗口轮数
- 当前消息列表

更新时机：
- 新建会话
- 切换会话
- 删除当前会话
- 会话重新命名

### 2. 当前待发送状态
用于表示本次还未发送出去的内容。

应包含：
- 输入框草稿
- 当前待发送附件
- 当前待发送引用托盘
- 当前网页上下文开关状态（后续预留）

更新时机：
- 用户输入文本
- 用户添加或删除图片
- 用户加入或删除引用片段
- 用户切换网页上下文状态

### 3. 当前 UI 状态
用于承载界面级的交互状态。

应包含：
- 当前是否正在发送
- 当前是否正在流式接收
- 悬浮按钮总开关
- 最近打开的会话

更新时机：
- 发起请求
- 请求结束
- 开关切换
- 会话切换

---

## 二、后端核心职责

### 4. 会话接口职责
后端需要提供会话管理能力，用于支持历史列表和会话切换。

主要职责：
- 创建会话
- 获取会话列表
- 获取单个会话详情
- 重命名会话
- 删除会话

这些接口服务于：
- 历史列表模块
- 新建对话
- 切换会话

### 5. 消息接口职责
后端需要支持消息读写与流式生成。

主要职责：
- 接收一条新消息请求
- 保存用户消息
- 调用 AI 层生成回复
- 流式返回模型结果
- 保存模型回复

### 6. 配置接口职责
后端需要支持用户相关配置能力。

主要职责：
- 读取用户设置
- 保存自定义动作
- 保存模型相关偏好
- 后续支持 BYOK 配置

## 三、核心请求类型

当前阶段建议围绕以下几类核心请求理解接口体系。

### 1. 获取历史会话列表
目标：
- 让侧边栏展示历史会话

请求大致包含：
- 当前用户身份或当前访客上下文

返回应包含：
- 会话标识
- 标题
- 当前默认模型
- 最近更新时间
- 消息总数

### 2. 获取单个会话详情
目标：
- 用户切换会话后加载完整内容

返回应包含：
- 会话元信息
- 消息列表
- 每条消息的角色、内容、时间、真实模型名
- 附件信息
- 当前默认模型

### 3. 新建会话
目标：
- 创建空白会话

返回应包含：
- 新会话标识
- 初始元信息

### 4. 发送文本消息
目标：
- 支撑最基础的文本问答链路

请求应包含：
- 会话标识
- 当前默认模型
- 默认历史窗口轮数
- 用户输入文本

可选附带：
- 当前引用托盘内容
- 当前网页上下文标记（后续预留）

返回方式：
- 流式返回模型回复

### 5. 发送图文消息
目标：
- 支撑图片问答

请求应包含：
- 会话标识
- 当前默认模型
- 默认历史窗口轮数
- 用户输入文本
- 当前待发送图片附件

发送前规则：
- 若当前模型不支持图片，应先阻止发送并提示切换模型
- 默认只携带最近 `10` 轮历史上下文

### 6. 保存或更新自定义动作
目标：
- 支撑 `options` 页动作管理

请求应包含：
- 动作名称
- 提示词
- 启用状态
- 排序信息

### 7. 更新当前默认模型
目标：
- 支撑会话内模型切换

请求应包含：
- 会话标识
- 新的默认模型

效果：
- 只影响下一次发送
- 不修改历史消息的真实模型名

## 四、流式回复设计

### 1. 为什么需要流式
当前产品主链路包含：
- 文本问答
- 图片问答

这两类都适合使用流式返回，以提升体感速度和持续反馈。

### 2. 当前流式链路
建议理解成以下过程：

1. 用户点击发送
2. 前端进入“正在发送/等待回复”状态
3. 后端保存用户消息
4. 后端调用 AI 层
5. AI 层开始返回流式内容
6. 前端逐步展示模型回复
7. 回复完成后，后端保存完整模型消息
8. 前端结束流式状态

### 3. 当前前端需要感知的几类流式状态
建议至少区分：
- 请求已开始
- 模型内容持续返回中
- 请求结束
- 请求失败

当前阶段不要求把流式事件设计得很复杂，只需要足够支撑消息逐步展示即可。

### 4. 流式完成后的正式落库
当前建议：
- 用户消息在请求开始时写入正式历史
- 模型消息在流式完成后写入正式历史

如果中途失败：
- 前端应能识别失败状态
- 后端可选择写入失败标记或由前端重试

## 五、图片、引用、模型切换如何进入同一请求链路

### 1. 文本消息
只包含：
- 文本输入

### 2. 文本 + 引用托盘
包含：
- 文本输入
- 一组 `ContextItem`

这些 `ContextItem`：
- 不是消息正文
- 而是独立的上下文对象

### 3. 文本 + 图片
包含：
- 文本输入
- 一组 `Attachment`

### 4. 文本 + 引用 + 图片
包含：
- 文本输入
- `ContextItem`
- `Attachment`

### 5. 模型能力校验位置
在正式发给 AI 层前，需要先判断：
- 当前模型是否支持“当前待发送内容 + 最近 10 轮历史上下文”

当前最重要的是图片校验：
- 有图片时，必须使用支持图片的模型
- 如果最近 `10` 轮历史里仍包含目标模型不支持的输入类型，则直接提示切换模型
- 当前阶段不做自动兼容、自动裁剪或自动降级处理

## 六、本地状态与云端状态的流转

### 1. 输入草稿
更新位置：
- 本地

更新时机：
- 用户输入文字时

正式进入云端时机：
- 用户点击发送，并成功生成正式用户消息后

### 2. 引用托盘
更新位置：
- 本地

更新时机：
- 用户点击 `引用`
- 用户删除某一段引用

正式进入云端时机：
- 用户点击发送
- 引用内容作为本次请求上下文提交

### 3. 待发送图片
更新位置：
- 本地

更新时机：
- 上传或拖拽图片
- 删除待发送图片

正式进入云端时机：
- 用户点击发送图文消息

### 4. 会话列表信息
更新位置：
- 云端主存储

更新时机：
- 创建会话
- 新增消息
- 重命名
- 删除会话
- 更新当前默认模型

### 5. 自定义动作
更新位置：
- 云端主存储

当前判断：
- 配置类数据更适合走云端保存
- 这样后续才便于同步和平台化

---

## 七、当前网页上下文开关的状态位置

当前网页问答的完整行为后续再细化，但从状态角度，当前建议先预留：

### 可预留的状态
- 当前网页上下文是否开启
- 当前页面标识或页面来源说明

### 当前阶段建议
- 可以先作为本地状态处理
- 后续如果网页问答进入当前版本重点，再决定是否进入正式会话上下文

### 当前不必定死的点
- 开关是按页面绑定还是按会话绑定
- 开启后网页内容何时抽取
- 是每次发送时抽取，还是开启时缓存

---

## 八、插件端与后端之间的边界

### 插件端负责
- 采集用户输入
- 管理本地草稿、引用托盘、待发送附件
- 展示历史会话
- 展示流式回复
- 触发模型切换和动作执行

### 后端负责
- 管理正式会话与消息数据
- 保存会话元信息
- 保存自定义动作
- 校验请求
- 调用 AI 层
- 返回流式结果

### AI 层负责
- 把产品层数据映射为模型输入
- 组织文本、附件、上下文
- 执行模型调用
- 返回回复结果

---

## 九、当前阶段不需要在本文件中展开的内容
- 最终 API 路径命名
- 请求字段命名细节
- 数据库存储实现
- LangChain 内部 state 结构
- PDF / 多网页 / RAG 的请求链路
- 网页答案高亮定位协议

## 当前使用建议
- 如果后续进入接口设计，应以本文件作为插件端与后端边界的基础。
- 如果后续进入实现，应先跑通“文本问答”与“会话列表”这两条最小链路。
- 如果后续要扩展网页增强能力，应在不打破本文件主链路的前提下增加上下文对象和局部状态。
